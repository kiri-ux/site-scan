How a scan works — for dev

Deterministic Python driving a real browser. No third-party APIs, no AI model in the scan path: every finding is a pattern match against a fixed endpoint list (signatures.py), so the same site scanned twice gives the same answer and any finding can be traced to a specific request at a specific timestamp. That reproducibility is the point — these reports go to clients on a compliance topic.

Three passes per page

Each in a fresh browser context, so no cookies or state carry over.

  1. Pre/post consent — load cold, record every request, click Accept, record again
  2. Reject — reload, click Reject, record what still fires
  3. GPC — reload with the Global Privacy Control signal set, record what fires anyway

Calls made

  • page.goto(url) ×3 — the three passes
  • HTTP GET of the raw HTML — pre-JavaScript source, to tell a hardcoded tag from an injected one
  • googletagmanager.com/gtm.js?id=… — published container JS, up to 3 per page, for fingerprint attribution
  • Everything else is passive: requests the page itself makes, observed through a listener

Stack

  • Playwright driving headless Chromium; Python / Flask; Postgres for scan history
  • Images, media and fonts aborted for speed — scripts, XHR and stylesheets always load
  • 15–40s per page, two pages concurrently

Bot restrictions — not circumvented

  • Desktop Chrome user-agent, 1366×900 viewport, en-US locale
  • Challenge screens detected by URL and page title (SiteGround sgcaptcha, Cloudflare)
  • On detection: asset blocking is disabled, the scanner waits up to 20s in-session, and retries twice
  • Still blocked → the scan is marked inconclusive and produces no findings
  • No fingerprint evasion, deliberately — it breaks on every vendor update and it is the wrong posture for a product sold to the people running these protections. The real fix is the three prerequisites below.

Known limits of the method

  • Load-time only — a tag that fires on scroll, click or form submit is not seen
  • One geography — whatever IP the scanner runs from; a site serving a different banner to EU visitors would look different from Europe
  • Accept is clicked by known selector or text fallback — when the fallback misfires, the reject and post-consent results become unreliable, which is why an unrecognized banner matters
  • Only recognizes what is in the signature list — an unknown vendor or a custom HTML tag is invisible. This is the gap the GTM API closes.

What the GTM API integration changes

Adds a fourth source, does not replace the scan

  • The scan sees what fired. The API sees what is configured. Neither answers the other's question — the value is in the join. A tag can be configured and never fire; a tag can fire that nobody knew was there.
  • Complete tag inventory — the scan only classifies pixels it recognizes by endpoint. A test container returned nine custom HTML tags the scan would never have identified. Biggest single gain.
  • Real consent configuration — whether a tag actually carries consent settings, rather than inferring gating from firing behavior.
  • Definitive container attribution — replaces the gtm.js fingerprint guess wherever access exists, and resolves what fingerprinting cannot: a tag that exists but has no firing trigger.

How it fits the scan path

  • Not inline. The quota is 0.25 QPS per project (25 requests per 100 seconds) and applies globally regardless of how many logins exist. An API read must never sit in front of a scan or be able to fail one.
  • Cache-first — on scan, look up the container's cached audit; if missing or stale, kick off a background read and store it. Common case costs nothing and a new client self-populates.
  • Reads the live published version, not the default workspace: a workspace can hold unpublished edits, so it does not describe what the site actually serves.
  • Degrades to fingerprint attribution — a container no Vici login can see is a normal outcome, not an error, and is the case client-owned containers will always land in.
  • Detail in the GTM API section further down this page.

Bot protection — what has to be in place before we sell this

Some hosts challenge the scanner instead of serving the page. Confirmed on gravensteinapplefair.com (SiteGround): the scan is redirected to a “Robot Challenge Screen” at /.well-known/sgcaptcha/ and never reaches the site. The scan is correctly marked inconclusive and produces no findings — but it also produces no data, and that is not a state we can ship to a paying client.

Three prerequisites

  1. A stable, documented egress IP — nobody can allowlist a rotating pool. Whatever infrastructure this ships on needs a fixed outbound IP, published so partners can hand it to a host. This has to land first or the other two are moot.
  2. An identifiable user-agent — something like ViciConsentScanner/1.0 (+https://vici…/scanner). Today the scanner presents as an anonymous desktop Chrome, which is exactly what bot protection exists to stop. Self-identifying makes allowlisting a simple request rather than an argument, and it matches the product's own pitch: we scan with the client's authorization.
  3. Allowlisting as an onboarding step — the scanner already flags a challenged scan unambiguously, so this becomes “before we can monitor this site, your host needs to allow our scanner,” pointing at a published page with the IP and user-agent.

Scope and open questions

  • A minority of clients, not most — the rest of the roster scans fine. Expect it on SiteGround, Cloudflare with Bot Fight Mode, Wordfence and Sucuri. On a WordPress-heavy book that is a meaningful minority.
  • Likely host-level, not our address — the challenged IP changed between runs (74.220.48.56, then .172), which points at a rule against the hosting range or automation fingerprinting rather than one flagged address. If so, waiting it out will not help.
  • Retrying makes it worse — every challenge hit re-arms the host's timer. The scanner now retries twice at 20s and stops.
  • Don't disguise the scanner — fingerprint evasion breaks on every vendor update, and it is the wrong posture for a product sold to the people running these protections.
  • Open: who owns the allowlist conversation — the partner or Vici ops? And does a client who refuses simply fall outside the monitored tier?

Product opportunity — consent-impact forecasting

The question advertisers ask before installing a CMP is “what does this cost me?” — in addressable audience, in conversion attribution, in reported ROAS. Every answer on the market today is a vendor estimate. With a panel of sites scanned before and after a banner goes in, Vici could answer it from measurement rather than assertion. That is a dataset that can only be accumulated, not bought, and it is the bridge between the scanner and the existing forecasting work.

Why this is ours to build

  • We know what was supposed to fire — every other scanner reports the trackers it finds. Only the agency that sold the campaign knows the expected set, which is what turns a fire rate into a measurable delta.
  • Before/after pairs come free — recurring scans already capture the same site either side of a CMP install. No extra instrumentation.
  • Forecasting infrastructure already exists — the waterfall and audience models are built; this supplies them with observed consent rates instead of assumed ones.
  • Answers a live objection — the most common reason a client refuses a banner is fear of losing measurement. A measured number closes that conversation either way.

What it needs, and what could go wrong

  • Scan continuity — the same pages, on a schedule, spanning the install date. Gaps make a pair unusable.
  • A defined metric — likely post-consent fire rate per product, plus pre/post pixel counts. Decide before collecting, not after.
  • Enough sites per vertical — consent rates vary widely by industry and banner design; a single blended number would be misleading.
  • Selection bias — sites that install a CMP are not a random sample. Any published figure needs that stated plainly.
  • Banner design is a confound — accept/reject placement moves consent rates more than anything else measured here. Record the CMP and banner type alongside the numbers or the comparison is meaningless.
  • Open: is this a client-facing forecast, a sales asset, or a published benchmark? The rigour needed differs a lot between the three.

Recurring scans — the value proposition after a client is fixed

A fixed static site rescanned daily returns the same green result forever, and a weekly “all clear” gets ignored inside a month. The value is not watching for the same problem to return — it is that the fixed state is fragile in specific, predictable ways, and every one of them is invisible until something looks. The fix is a moment; the site keeps changing.

What recurring scans actually catch

  • Measurement — a pixel that stopped firing is caught in a day rather than at the end of a reporting cycle. New product pixels are confirmed live after launch. This protects the data Vici optimizes and reports on, and is the strongest argument of the four.
  • Change detection — a site redesign or CMS update drops the tracking; someone adds a tag outside the container; CMP settings reset after a plugin update.
  • Compliance drift — new tags appear ungated after the fix, a banner quietly stops gating, or a new state law starts applying to an existing client.
  • Proof over time — a dated scan history showing the site was configured correctly, evidence if a claim ever arrives, and a before/after record of when remediation happened.

What this means for the build

  • Report only on change — this is the requirement that makes recurring defensible. Silence when nothing moved, an alert when something does. The scanner currently produces a full report every run regardless, which trains people to ignore it.
  • Needs a diff, not just a history — run-over-run comparison per client: pixels that stopped firing, tags that appeared, CMP or Consent Mode changes, state checks that flipped. The run pills already store the history; nothing computes the delta.
  • Cadence should follow spend, not a flat subscription — weekly is enough to catch a redesign for a client with active spend; a dormant client does not need surveillance. Nothing about these sites changes hourly.
  • Scan on the event, not only the schedule — after a redesign, a new product launch, or a CMP change. That is when findings actually appear, and it is a natural hook into the orders system.
  • Open: what counts as a change worth alerting on, and who receives it — the buyer, the partner, or both?

GTM API — state of play and the production target

A working read path exists and has been proven end to end against live containers. The prototype is a standalone script (gtm_api.py), not wired into the scanner. What follows is what was built, what was tried and rejected, and how it should be built for production.

Proven so far

  • Cloud project — dedicated project, Tag Manager API enabled. Separate from the general-purpose project on purpose: this credential can eventually publish tags to client sites, so its blast radius should be its own.
  • OAuth, not a service account — see the next panel. Consent screen is Internal, which skips Google app verification entirely.
  • White-labeled identity — logins live on a secondary domain in the same Workspace org, so nothing partner-facing carries the parent brand while the accounts stay centrally administered.
  • Multi-login merge — Google caps how many GTM accounts one login can join, so several logins are authorized and their views merged into one index keyed by GTM public ID. Overlap is expected and handled: first login claims a container, the rest are recorded as fallbacks.
  • Live read confirmed — 279 containers reachable from one account; a container read returned its full tag list with consent settings, firing triggers and paused state.
  • Reads the LIVE version, not the default workspace — a workspace can hold unpublished edits, so it does not describe what the site actually serves, and what the site serves is what the scanner observes.

Tried and rejected: service account

  • Why it was the first choice — no consent flow, no per-user token, standard for automated access.
  • Why it fails here — a service account must be invited to every GTM account individually. With hundreds of partner-named accounts and new ones added regularly, that is a permanent chore with a guaranteed failure mode: the invite nobody remembers. An OAuth token inherits the access its login already has, including accounts created tomorrow.
  • Secondary cost — the org blocks downloadable service account keys by default (Secure by Default). Working around that meant weakening an org policy for no lasting benefit. The override has been reverted and the service account deleted.
  • Where it still fits — a client who owns their own GTM account and will grant narrow access rather than full membership.

Production target

Build it this way

  • Cache-first, not a nightly sweep — the earlier plan was an estate-wide overnight job. Simpler and cheaper: on scan, look up the container's cached audit; if missing or stale, kick off a background read and write it to storage. Common case costs nothing, a new client self-populates, and no cron job is needed until estate-wide data is wanted for its own sake.
  • Never inline in the scan path — the quota is 0.25 QPS per PROJECT (25 requests per 100 seconds), so calls queue globally no matter how many logins exist. A background write that fails must never break a scan.
  • Store keyed by GTM public ID — with a fetched-at timestamp. The report should say how old an audit is rather than presenting stale configuration as current.
  • Degrade to fingerprint attribution — a container nobody can see is a normal outcome, not an error. The scanner's existing per-container corpus matching stays the fallback and is the only method that works on client-owned containers.
  • Read-only scope until the write side is genuinely needed — a refresh token covering hundreds of client containers is a serious credential. Keep it unable to publish for as long as possible.
  • Secrets, not config — the OAuth client JSON and the refresh tokens are production secrets. They were kept off shared drives during prototyping and should stay that way.

What it unlocks, and what is still open

  • Complete tag inventory — the scan only sees pixels it recognizes by endpoint. A test container returned nine custom HTML tags the scan would never have classified. This is the biggest single gain.
  • Real consent configuration — whether a tag actually has consent settings, rather than inferring gating from firing behavior.
  • Definitive container attribution — replaces fingerprint inference where access exists, and resolves the case fingerprinting cannot: a tag that exists but has no firing trigger.
  • Open: coverage. Each GTM account needs a login added before it appears. Which accounts are Vici-controlled versus client-owned should be recorded as it is done — it drives the ownership tag on the report.
  • Open: staleness policy. How old may an audit be before the report stops relying on it?
  • Open: the write path. Applying the consent procedure via the API is the natural next product. It needs edit.containers, edit.containerversions and publish, and every login re-authorized. Strong recommendation: stop at a created version and let a human publish, at least until it has proven itself.

Already handled in the scanner

  • Challenge screens are detected by URL and page title (SiteGround, Cloudflare) and waited out in the same browser session before the scan gives up.
  • A scan that finds nothing at all is marked inconclusive rather than reported as absence, so a blocked run never generates false “install or repair the pixel” work.
  • Inconclusive scans report what was actually received — HTTP status, page title, HTML size and any redirect — so the cause is visible without a code read.
